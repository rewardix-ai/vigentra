# Vigentra API: every endpoint, its HTTP method, and why

This covers the central API (`services/central-api`, 61 operations), the browser-facing proxy, and the two mock
department systems. For each endpoint it gives the method, what the endpoint does, why that method fits, and
why the alternatives do not. The full request and response shapes are in [api.md](api.md); the live list is
the OpenAPI page at `http://localhost:8000/docs`.

## The rules we follow

| Method | We use it for | Safe (changes nothing) | Idempotent (repeat = same result) | Count |
|---|---|---|---|---:|
| **GET** | Reading data: lists, one record, reports, counts, video segments | Yes | Yes | 39 |
| **POST** | Creating something new, and actions that start a workflow or record an event | No | No (made safe where it matters) | 17 |
| **PATCH** | Changing some fields of an existing record | No | Yes, as we use it | 2 |
| **DELETE** | Ending something: a video session, an access grant, a watchlist entry | No | Yes | 3 |
| PUT | Not used anywhere | | | 0 |

What these choices give us:

- **A read is always a GET, so it never changes anything.** Browsers, proxies and the dashboard can repeat,
  prefetch or retry a GET with no risk. Nothing can be created or changed by someone opening a link.
- **Anything that changes state is a POST, PATCH or DELETE.** Those always need a signed-in session, the right
  permission, and they write an audit row.
- **Secrets never travel in a URL.** URLs end up in browser history, server logs and proxy logs. That is why
  sign-in is a POST with the password in the body, and why no GET takes a credential.
- **Status codes say what happened:**
  - `200` for a read or an action;
  - `201 Created` when a new record now exists;
  - `202 Accepted` when the server only noted something;
  - `400` / `422` when the request itself is wrong (for example, a plate not shaped like an Indian registration);
  - `401` / `403` when the caller is not signed in or not allowed;
  - `404` when the record is unknown;
  - `409 Conflict` when the record is in the wrong state for the action (a form that is not a draft, a duplicate entry);
  - `410 Gone` when a video session has expired or been revoked: it existed, and it will never stream again.

### Why there is no PUT

PUT means "replace this whole record with what I send, at this exact URL". Nothing in Vigentra should work
that way:

- **Records are owned elsewhere.** A camera record belongs to its department's system. Replacing it wholesale
  from Vigentra would overwrite the department's data.
- **Records have server-controlled fields.** These are status, who raised the record, validation results and
  timestamps. With PUT the client would have to send them back, and could change them.
- **New records get their ID from the server.** PUT needs the client to know the final URL in advance, and our
  IDs are generated by the server.
- **Partial edits are what users actually do.** Fixing a typo in a draft is a change to one field. That is PATCH.

### Why actions are POST to a sub-path, not PATCH on a status field

Submitting a form, granting access or acknowledging an alert is a **step in a workflow**, not a field edit.
Each step:

- checks who is asking (only the owning unit may grant; only the raiser may submit);
- checks the current state (only a draft can be submitted);
- can run work in another system (validation runs inside the department's VMS);
- writes a specific audit entry.

So each step is its own endpoint, for example `POST /installation-requests/{id}/submit`.

If clients could instead `PATCH {"status": "APPROVED"}`, they could jump any form to any state and skip the
checks. One clear POST per allowed step means the server enforces the workflow, and the audit log says exactly
which step was taken.

## 1. Sign-in and the signed-in account

| Method | Path | What it does | Why this method, and not another |
|---|---|---|---|
| POST | `/api/v1/auth/login` | Swaps a username and password for a signed token (a JWT) | **POST:** the password goes in the request body, not the URL, so it is never in history or logs. A new token is issued on each call, so it is not a read. GET would expose the password; PUT and PATCH make no sense for "create a session". |
| GET | `/api/v1/auth/me` | Who is signed in: role, department, permissions | **GET:** a pure read of the caller's own account; safe to repeat on every page load. |

## 2. Department systems and the camera registry

| Method | Path | What it does | Why this method |
|---|---|---|---|
| GET | `/api/v1/sources` | The federated department systems and their state | Read only. |
| POST | `/api/v1/sources/sync` | Pulls approved camera metadata from every department system now | **POST:** an action that writes to the registry and calls other systems; each run is a new sync with its own result and audit row. A GET that writes would break the rule that reads are safe: a crawler or prefetch could start syncs. |
| GET | `/api/v1/cameras` | Every camera in the canonical shape, with filters | Read; filters are query parameters, so a filtered list is a shareable link. |
| GET | `/api/v1/cameras/{camera_id}` | One camera record | Read one resource by its ID. |
| GET | `/api/v1/cameras/{camera_id}/health` | Asks the owning department for the camera's health, or returns the last stored check | Read. It contacts the department but changes nothing there. |
| GET | `/api/v1/cameras/{camera_id}/access-policy` | Who may view the camera's footage, and what Vigentra grants | Read. It describes a policy and grants nothing. |
| GET | `/api/v1/cities` | Cities in the registry, with departments and zones | Read. |
| GET | `/api/v1/departments` | Departments this account may see | Read. |
| GET | `/api/v1/overview` | Counts for the operations overview | Read. |

## 3. Installation forms (new cameras)

The form lives in the department's own system; Vigentra relays it.

| Method | Path | What it does | Why this method |
|---|---|---|---|
| POST | `/api/v1/installation-requests` → **201** | Creates a draft form | **POST:** creates a new record whose ID the department's system assigns. PUT would need the client to choose the ID. 201 tells the client the record now exists. |
| GET | `/api/v1/installation-requests` | Lists forms | Read. |
| GET | `/api/v1/installation-requests/{request_id}` | One form | Read. |
| PATCH | `/api/v1/installation-requests/{request_id}` | Edits some fields of a draft (or a returned form), by its raiser only | **PATCH:** only the changed fields are sent; status, raiser and validation results stay under server control. PUT would force the whole form to be resent and could overwrite those fields. Sending the same edit twice gives the same result. |
| POST | `/api/v1/installation-requests/{request_id}/submit` | Sends the form for the department's validation | **POST action:** starts validation inside the department's system, and the result can be VALIDATION_FAILED with the department's error list. A workflow step, not a field edit. |
| POST | `/api/v1/installation-requests/{request_id}/suspend` | Takes a commissioned camera out of service | **POST action:** a state change with rules (only commissioned cameras) and its own audit entry. |
| POST | `/api/v1/installation-requests/{request_id}/decommission` | Retires the camera permanently | **POST action**, not DELETE: the asset record must remain (it is a government asset register). Only its state changes. DELETE would mean the record is gone. |
| POST | `/api/v1/installation-requests/{request_id}/sync-metadata` | Pushes this one record into the central registry now | **POST action:** a sync for one record, with the same gate as the full sync. |

## 4. Detections, events, incidents (from the edge)

| Method | Path | What it does | Why this method |
|---|---|---|---|
| POST | `/api/v1/detections/ingest` | An edge worker sends a batch of detections and plate readings | **POST:** many new records in one call; the server decides each row's outcome. It is **made safe to retry**: every detection has an ID derived from its camera, frame and box, so a resent batch is reported as duplicates rather than stored twice. A worker that lost its connection can simply send again. PUT cannot express "create these 200 records". |
| POST | `/api/v1/detections/frame-quality` → **202** | An edge worker reports a degraded frame (dark, overexposed, …) | **POST:** a new observation. **202 Accepted**: the server notes it; there is no new resource to fetch back. |
| POST | `/api/v1/incidents/ingest` | The edge submits incident candidates (wrong way, sudden stop, intrusion, …) | **POST batch**, safe to retry for the same reason as detections. |
| GET | `/api/v1/detections` | Detections this account may read | Read with filters. |
| GET | `/api/v1/detections/{detection_id}` | One detection | Read. |
| GET | `/api/v1/cameras/{camera_id}/detections` | Detections for one camera | Read. |
| GET | `/api/v1/cameras/{camera_id}/traffic` | Vehicles counted at a camera, by class (counted in the database) | Read. Counting on the server instead of downloading every row is the performance gain; the method stays GET. |
| GET | `/api/v1/detector/health` | The analytics setup and the last model build seen | Read. |
| GET | `/api/v1/events` | Normalised events from every source | Read. |
| GET | `/api/v1/events/correlation` | Events at nearby cameras within a short time window | Read; a computed answer, nothing stored. |
| GET | `/api/v1/incidents` | Incident candidates, newest first | Read. |
| PATCH | `/api/v1/incidents/{incident_id}` | An operator records a review: REVIEWING, CONFIRMED or DISMISSED, with a note | **PATCH:** it sets two fields (status and note) on an existing incident, and a reviewer can change their mind (REVIEWING → CONFIRMED). The rest of the incident (what the edge saw) must not change, which PUT could not guarantee. Contrast with alert acknowledgement (below), which is a one-way event and so a POST. |

## 5. Video access, sessions and streams

| Method | Path | What it does | Why this method |
|---|---|---|---|
| POST | `/api/v1/video-access-requests` → **201** | Asks the owning unit for access to one of its cameras | **POST:** creates a new request with a server-assigned ID. |
| GET | `/api/v1/video-access-requests` | Requests I raised, and requests against my unit | Read. |
| POST | `/api/v1/video-access-requests/{grant_id}/grant` | The owning unit says yes | **POST action:** only the camera's own unit may do it; it starts a time-limited grant and is audited. A PATCH of `status` would let anyone who can edit the record approve it. |
| POST | `/api/v1/video-access-requests/{grant_id}/deny` | The owning unit says no | **POST action**, as above. |
| DELETE | `/api/v1/video-access-requests/{grant_id}` | Withdraws a request or revokes a live grant (either side) | **DELETE:** the effect is "this access no longer exists". Repeating it changes nothing, so it is idempotent. The record itself is kept (marked revoked and audited) because the trail is evidence; DELETE describes the access ending, not the row vanishing. |
| POST | `/api/v1/video-sessions` → **201** | Opens a short-lived, audited video session after checking role, department, city, zone, camera state and the owner's policy | **POST:** each call creates a new session with its own ID, expiry and audit row, so calling twice means two sessions, which is not idempotent. GET would let a link or prefetch open video sessions. |
| GET | `/api/v1/video-sessions/{session_id}/status` | Session state and time left (drives the player's countdown) | Read; reports expiry without raising an error. |
| DELETE | `/api/v1/video-sessions/{session_id}` | Stops a session immediately; that ID never streams again | **DELETE:** ends the session. Idempotent: stopping a stopped session is still stopped. |
| GET | `/api/v1/streams/{session_id}?p=…` | The brokered video itself: playlists and segments, proxied from the department | **GET:** video players (HLS) only ever fetch with GET, and a segment is a read. **Permission is re-checked on every segment**, so revoking access stops a playing stream within one segment. The browser never learns the camera's real address. |
| GET | `/api/v1/cameras/{camera_id}/snapshot` | Latest still frame for the live wall | Read; an image the browser can load directly. |

## 6. Watchlist, alerts, plates and tracing

| Method | Path | What it does | Why this method |
|---|---|---|---|
| GET | `/api/v1/watchlist` | Watchlist entries | Read. |
| POST | `/api/v1/watchlist` → **201** | Adds a registration number, refusing anything not shaped like an Indian plate | **POST:** a new entry with a server-assigned ID. |
| DELETE | `/api/v1/watchlist/{entry_id}` | Stands an entry down | **DELETE:** the entry stops matching from now on. Internally it is marked inactive, never erased, so past alerts still point to it and the audit trail stays complete. Idempotent. |
| GET | `/api/v1/alerts` | Watchlist alerts, sorted by priority | Read. |
| GET | `/api/v1/alerts/open-count` | How many alerts are waiting (the sidebar badge, polled every 15 s) | **GET, and a separate endpoint:** polling the full list wrote an "alerts viewed" audit row every 15 s on every page. A count discloses nothing, so it is not audited. |
| POST | `/api/v1/alerts/{alert_id}/acknowledge` | Closes an alert as acted on, or dismissed with a reason | **POST action:** a one-way event that records who closed it, when and why. It is not a reversible field edit like an incident review, so not PATCH. |
| GET | `/api/v1/sightings` | Plate sightings | Read. |
| GET | `/api/v1/plates/search?q=…` | Plates the network saw near an uncertain query (tolerates misreads) | Read; a computed ranking. |
| GET | `/api/v1/plates/{plate}/track?reason=…` | A vehicle's route in time order, with leg speeds | **GET:** it reads and computes, and changes no data. A **reason is mandatory** and the trace is audited, because it is the most revealing question the platform answers. The audit row is a record *of* the read, like an access log, not a change to the data being read. |
| GET | `/api/v1/vehicles`, `/vehicles/facets`, `/vehicles/{registration_number}` | Search and look up the (synthetic) vehicle registry | Read. |

## 7. Health alerts, reports, audit and system

| Method | Path | What it does | Why this method |
|---|---|---|---|
| GET | `/health` | Platform and dependency health (for Docker and load balancers) | Read; health checkers only use GET. |
| GET | `/` | Service banner | Read. |
| GET | `/api/v1/health-alerts` | Cameras and department systems that stopped answering | Read. |
| GET | `/api/v1/health-alerts/open-count` | How many are down and not yet taken up | Read; separate for the same reason as the alert badge. |
| POST | `/api/v1/health-alerts/{alert_id}/acknowledge` | "Someone is on it": the NOC desk or the owning unit takes the alert | **POST action:** a one-way, audited event. The monitor closes the alert itself when the camera answers again. |
| GET | `/api/v1/reports/gap-analysis` | Coverage gaps and ageing infrastructure | Read. |
| GET | `/api/v1/reports/anpr` | The ANPR output report: plates with timestamps, camera, location, watchlist hit | Read. The report the challenge asks for. |
| GET | `/api/v1/audit` | The audit trail | **Read only.** The audit log has no POST, PATCH or DELETE at all: rows are written by the server as things happen and can never be edited or removed through the API. |

## 8. The browser-facing proxy (dashboard)

The console in the browser never calls the central API directly.

| Method | Path | What it does | Why |
|---|---|---|---|
| POST | `/api/auth/login` | Signs in and puts the token in an **httpOnly cookie** | POST for the same reason as `/auth/login`. The cookie cannot be read by page scripts, so an injected script cannot steal the token. |
| POST | `/api/auth/logout` | Clears the cookie | POST so that a link or an image tag cannot sign someone out. |
| GET, POST, PATCH, DELETE | `/api/vigentra/*` | Forwards each call to the central API with the token from the cookie | It forwards exactly the four methods the central API uses, no more; PUT is not forwarded because nothing accepts it. |

## 9. The mock department systems

These stand in for two different vendors' VMS, and use the same method rules in their own dialects:

| Methods | Traffic Police VMS (`X-API-Key`) | Municipal VMS (Bearer token) |
|---|---|---|
| GET | camera lists, health, live and playback handles, events, installation records | the same, under `/vms/…` |
| POST | create a form; submit, suspend, decommission, mark-synchronized; admin status | the same |
| PATCH | edit a draft form | edit a draft form |

Vigentra's adapters translate each vendor's paths and payloads into the canonical calls above, so the
central API's method rules stay the same whatever the vendor does.

## Benefits, in one place

- **Safety of reads.** 39 of 61 operations are GET and can never change data. Caches, retries, prefetching and
  shared links are all harmless.
- **Retries without duplicates.** Edge workers send batches by POST, made safe to repeat with deterministic
  IDs. A dropped connection never double-counts a vehicle or a plate.
- **Workflows the server enforces.** Every workflow step is its own POST, checked for permission and state,
  so no client can skip validation or approve its own request.
- **Partial edits that cannot clobber.** PATCH changes only the fields sent; status, ownership and history
  stay under server control.
- **Endings that keep evidence.** DELETE ends access, sessions and watchlist entries, but the record stays,
  so the audit trail is complete.
- **No secrets in URLs.** Credentials only travel in request bodies, and tokens only in an httpOnly cookie.
