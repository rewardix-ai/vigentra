Vigentra · Gujarat Police Innovation Challenge 2026

How the Vigentra code works

Vigentra joins CCTV cameras owned by different departments into one platform. It keeps the camera register, shows authorised video, reads number plates at the edge, matches them against a watchlist and raises alerts. This guide walks through the code that does each of those, service by service, with the file to open for every step.

Paths are relative to the repository root, vigentra/. Line numbers are given where a function is worth opening. Everything here was read from the code as it stands on 1 October 2026.

The big picture

Three ideas shape the whole codebase.

  • Federate, don't replace. Each department keeps its own cameras and video system. The central API reaches them through one adapter per system and keeps only metadata: where a camera is, who owns it, whether it is online.
  • Analyse at the edge. Video is read next to the camera by an edge worker. Only results travel to the centre: boxes, plate readings, incident candidates.
  • One console, every look audited. People use one dashboard. Watching video needs a reason and the password again, goes through a short-lived brokered session, and every view, search and alert is written to the audit log.

In the stack that ships today, the 30 Sentinel grid cameras are registered to the Traffic Police and the Municipal Corporation through the grid adapter. The Traffic Police's own VMS is a third source, carrying the Delhi test clip and 19 public TfL traffic cameras. That makes 50 cameras in service.

One plate, start to finish

This is the path that the hackathon's central requirement depends on: a live camera, a plate read, a watchlist match and an alert.

  1. Frames. The worker opens the camera over RTSP on TCP and times every frame by its presentation timestamp (PTS), never by when it arrived. services/edge-worker/app/grid.py, ReconnectingCapture.frames (line 468).
  2. Tracking. Each frame goes into the ANPR engine, which finds and tracks vehicles and banks crops of each vehicle's plate. app/anpr_engine.py, process.
  3. The verdict. When a vehicle has been out of sight for the tracker's buffer, its track closes. The engine then votes across all its plate crops and checks the result against Indian plate grammar. The worker receives a settled plate on the frame it settled.
  4. Upload. A frame that settled a plate is uploaded at once; plain boxes wait for a batch of 50. If the sign-in has expired, the worker signs in again and retries once. app/worker.py, _should_flush and _post_signed.
  5. Ingest. The API checks that the camera exists, is commissioned and is in the worker's scope, stores the detection and a plate sighting, and matches the plate against the active watchlist. services/central-api/app/routers/detections.py line 155, services/watchlist_service.py record_sightings line 145.
  6. Alert. A match becomes an alert, committed in the same transaction as its evidence, audited as a machine decision, and posted to a signed webhook. The alerts page shows it within 5 seconds, most urgent first.
  7. Route. From the alert an officer can trace the vehicle: every sighting of that plate across cameras, timestamped, on a map. services/track_service.py reconstruct line 208.

Central API

The central API is the middle of everything. It never stores video and never runs computer vision. It holds the register, decides who may see what, brokers video, receives results from the edge, and keeps the audit trail.

Start-up and layers

Start-up happens in services/central-api/app/main.py, function lifespan (lines 123–258). It creates the tables, seeds roles and demo users, builds one shared grid client and the adapters, runs a first sync, imports reference vehicle data and starts the health monitor. The grid allows only one session per account, which is why there is exactly one shared grid client.

Each request then passes through three layers:

  • Routers (app/routers/) handle HTTP. Each checks the caller's permission with require_permission and calls a service. They are grouped as registry (auth, sources, installation requests, cameras, directory, overview, reports, events, health, audit), video (grants, sessions), analytics (detections, incidents, watchlist) and vehicles.
  • Services (app/services/) hold the logic: sync_service, health_monitor, installation_service, policy_service, video_permissions, video_grants, video_broker, watchlist_service, plate_matching, track_service, alert_webhook, audit_service.
  • Models and schemas. models.py defines the tables, schemas.py the API's canonical shapes, and mappers.py turns a database row into an API response, removing detail the caller may not see.

Beside them sit the adapters (app/adapters/): base.py is the contract every source implements, and grid_adapter.py, traffic_adapter.py and municipal_adapter.py each translate one source's dialect into the canonical camera. config.py holds settings, the role-to-permission table ROLE_PERMISSIONS (line 139) and the list of federated sources (line 775).

The six flows

1. Camera metadata sync and health.

  1. Sync runs at start-up and on POST /api/v1/sources/sync, calling sync_all (services/sync_service.py line 423).
  2. Every source is polled at once (_collect, line 88). Each adapter turns its vendor's JSON into the canonical camera. The grid adapter caches the grid's camera list behind its one shared sign-in.
  3. A source that cannot be reached marks only its own cameras offline (lines 469–485). The others keep working.
  4. _upsert_camera (line 195) writes the camera, a health sample and its policy, and refuses an ID that clashes with another source's camera.
  5. A camera a source stops publishing is removed, but only after a clean read of that source (lines 533–553).
  6. The health monitor (services/health_monitor.py) runs every 20 seconds, polls sources and cameras, and prunes samples older than 6 hours. GET /health needs no sign-in.

Camera sync · services/central-api/app/services/sync_service.py, health_monitor.py

2. Watching a camera.

  1. To watch another unit's camera, an officer asks first: POST /api/v1/video-access-requests. Only the owning unit can grant or deny (services/video_grants.py); a grant lasts 7 days.
  2. POST /api/v1/video-sessions asks for the password again and a reason.
  3. evaluate (services/video_permissions.py line 71) checks, in order: the account is active, the role allows video, the camera is commissioned and healthy, the camera is the caller's own unit's or a grant exists, and the city and zone match.
  4. The broker (services/video_broker.py create_session, line 126) fetches a handle from the source and keeps it on the server. Live sessions last 5 minutes, playback 15, and both are watermarked and audited.
  5. GET /api/v1/streams/{id} serves the stream only to the session's owner, and re-checks permission on every request, so revoking a grant stops a playing stream.

Watching a camera · routers/video_sessions.py, services/video_permissions.py evaluate, services/video_broker.py

3. Detection to alert. Covered step by step in One plate, start to finish. The matcher (services/plate_matching.py) uses an edit distance in which known OCR confusions such as B and 8 or O and 0 cost 0.35 and an unrelated character costs 1.0, with a threshold of 1.0. Priority is worked out when an alert is read, not stored: an exact read of a stolen or wanted vehicle is critical, any other exact read is high, and a near match is review (schemas.py lines 1453–1463).

Detection to alert · routers/detections.py ingest_detections, services/watchlist_service.py record_sightings, services/plate_matching.py, services/alert_webhook.py

4. Tracing a vehicle. GET /api/v1/plates/{plate}/track needs the track:read permission and a written reason of at least 8 characters. reconstruct (services/track_service.py line 208) uses only cameras the caller may read, merges repeated reads at one camera within 90 seconds into one pass, and flags any leg faster than 200 km/h instead of dropping it. History starts no earlier than the plate retention window, 30 days by default.

5. Onboarding a camera.

  1. POST /api/v1/installation-requests creates a draft in the department's own VMS, never in the read-only grid (services/installation_service.py).
  2. The installer edits the draft and submits it. The department validates it and either rejects it or registers the camera.
  3. Registration triggers an immediate sync of that source, and the camera appears in the registry. The next full sync marks it synchronised.
  4. Suspending or decommissioning keeps the record, marked unavailable with video switched off.
  5. Bulk onboarding is a CSV upload in the dashboard, which creates and submits each row in turn.

Onboarding a camera: the request's life · services/installation_service.py, the department's own VMS, services/sync_service.py

6. Sign-in, roles and audit. POST /api/v1/auth/login checks the credentials and issues a signed token (JWT, valid 12 hours) carrying role and department. On every request get_current_user re-reads the account, so a role change applies at once. There are 13 roles and 22 permissions, and scope is checked by department, city and zone. audit_service.record writes and commits each audit row on its own, so a refused attempt is recorded even when the request fails.

Edge worker

The edge worker runs next to the video. It reads frames, runs the ANPR engine and incident rules, and uploads only metadata. It is authorised like a person: it signs in, and opens an audited video session for every camera it reads.

The loop

  • supervise (app/worker.py line 1008) signs in with backoff, fetches the camera list every cycle, loads one detector and one engine cache for all cameras, and carries on when one camera fails.
  • run (line 583) does one camera pass. It gets that camera's engine, builds the frame-quality router and frame budget from the camera's profile, opens the session and picks a frame source. Then, per frame, it applies the sampler, skips badly degraded frames, runs the engine, builds detection payloads, updates incidents, and uploads when _should_flush says so.
  • _finish_pass (line 442) settles the remaining tracks and uploads them. If that upload fails, the plates it lost are logged as an error.

Reading the Sentinel grid

The grid's integrator guide sets rules, and app/grid.py follows them one by one:

  • RTSP is forced onto TCP, with a 10-second socket timeout (_force_tcp_transport, line 109). If the RTSP port does not answer within 3 seconds, the worker fails loudly rather than fall back to HLS (open_capture, line 561).
  • Timing comes from PTS only (line 503). The declared frame rate is never trusted.
  • 25 failed reads trigger a reconnect, with backoff from 2 to 30 seconds. No frame for 90 seconds ends the pass.
  • The grid's recordings loop. A PTS jump backwards of more than 5 seconds is treated as the loop point: the engine's tracks and the incident state are reset, so two different vehicles are never spliced into one plate history.
  • Camera URLs are built from the documented pattern. The worker deliberately does not sign in to the grid's web gateway, because a second sign-in would sign the central API out.

Reading the grid · services/edge-worker/app/grid.py: open_capture, _force_tcp_transport, ReconnectingCapture.frames

Uploading

Boxes are batched 50 at a time; a settled plate goes up with the frame that settled it; incidents go up on the frame that raised them. Detection IDs are deterministic, so a repeated upload collapses into the same row, and several workers can share the load without double counting. _post_signed (line 346) signs in again once if the session has expired.

The other edge services

  • detector-traffic and detector-municipal run plain YOLO11n object detection on every camera, around the clock, one per department's AI account. They count objects; they read no plates.
  • grid-snapshots runs tools/snapshot_wall.py: it decodes grid streams only for cameras someone is watching and serves each camera's latest frame, with detections drawn, to the live wall.

ANPR engine

The engine reads a vehicle, not a frame. It follows each vehicle across every frame it appears in, collects crops of its plate, and decides once, when the vehicle has gone. The guiding rule is that a wrong plate is worse than a missing one: a plate that cannot be read is refused, not guessed.

The 15 stages

In order, mostly in services/edge-worker/anpr/pipeline.py:

  1. Frame sampling. Every nth frame, plus a burst of 24 consecutive frames whenever a vehicle is close enough for its plate to be read. anpr/sampling.py.
  2. Overlay mask. The camera's burned-in clock and captions are masked: fixed rectangles from roi.yaml, text found by a temporal-variance check, and plate-like boxes that never move near the top or bottom edge.
  3. Vehicle detection and tracking. YOLO11s with ByteTrack, following cars, motorcycles, buses and trucks at the frame's own resolution. anpr/detect/vehicle.py.
  4. Plate detection inside the vehicle. Only vehicles at least 96 px wide are searched. A geometry prior penalises boxes with the wrong shape or position, or wider than 0.60 of the vehicle, and each plate belongs to one vehicle. anpr/detect/plate.py.
  5. Crop bank. Each track keeps up to 64 crops, ranked by quality times detector confidence. Signs and hoardings are rejected, and plate corners are estimated. anpr/track/crop_bank.py, anpr/enhance/quality.py.
  6. Legibility gate. When a track closes, its best crop must be at least 22 by 8 px and sharp and contrasty enough; otherwise the track is marked unreadable.
  7. Per-crop reads. Every crop at least 24 px wide is read on its own. Only reads that look like a full registration of a known state and district are kept.
  8. Rectify and enhance. The best 12 crops are straightened, aligned, fused into a sharper image, and cleaned of glare, noise and blur. Squat boxes are also tried as two-row plates.
  9. Readers. Two CRNN character readers with a grammar-guided decoder, plus an optional whole-plate text reader (PaddleOCR) when PaddlePaddle is installed. anpr/read/.
  10. Fusion. ROVER aligns the readers' strings and votes character by character. Strings that look like timestamps or captions are rejected. anpr/fuse/rover.py.
  11. String vote and confirm rules. Explained in the next section. _vote_pick (line 824) and _decide (line 991).
  12. Glyph check. The best crops must show at least 3 glyph-shaped marks. This stopped a windscreen being "read" as a plate. anpr/detect/char_evidence.py.
  13. Indian plate grammar. Formats, state codes, Gujarat RTO codes and district ranges, from config/india_codes.yaml; a state other than the camera's own is down-weighted. anpr/plate_grammar.py.
  14. Fragment merging. At the end of a pass, fragments of one vehicle that read the same plate are joined and decided again together.
  15. One plate per vehicle. Only confirmed reads above the review score and grammar floor leave the engine, and each vehicle is reported once. app/anpr_engine.py.

The ANPR engine, per frame · services/edge-worker/anpr/pipeline.py process_frame, _finalise_track; app/anpr_engine.py process, _harvest. At the end of a pass, flush closes every open track the same way and then merges fragments that read the same plate.

When a plate is confirmed

A reading becomes a confirmed plate by one of these routes, tried in order:

  • Two kinds of reader agree. A CRNN and the text reader each read the same string on at least 2 crops, 6 in total, with no stronger rival within 2 characters. Two CRNNs agreeing is not enough, because they share their mistakes.
  • The string vote. At least 4 crops, at least 40% of the vote, and the runner-up under half the winner. A vote another reader contradicts is never confirmed.
  • The fused reading. Otherwise the ROVER result must reach confidence 0.75, with 6 hypotheses, every character's vote at least 0.5, and at least 3 frames agreeing.

When a plate is confirmed · anpr/pipeline.py _vote_pick (line 824) chooses the route, _decide (line 991) applies the floors. Anything not confirmed stays a candidate: shown for review, never sent as a plate to act on.

Every route also needs a plate at least 40 px wide and the glyph check. Measured on 38 recorded clips, this reads 36 of the 48 plates a person can read and confirms no false plate.

Per-camera settings

Cameras differ, so config/camera_profiles.yaml holds per-camera overrides, found by camera ID or alias and merged over the defaults (anpr/camera/profile.py). A profile may set:

  • thresholds, any engine threshold. The Delhi camera sets its home state to DL.
  • sampling. Cameras with legible plates get every second frame for 150 frames; the rest keep the sparse default.
  • frame_quality, the low-light handling, off by default.
  • intrusion, a restricted zone: a polygon, the classes it applies to, a dwell time and the hours it is armed.

Incidents

anpr/incidents.py watches the tracker's boxes and raises candidates for a person to confirm. Speed is measured in vehicle heights per second, and each track and kind has a 20-second cooldown.

KindRaised when
Sudden stopstrong deceleration, then nearly still
Stopped in lanewas moving, then still for 6 s while other traffic moves
Wrong wayheading at least 115° away from the flow learned over 12 or more tracks
Collision candidatetwo boxes overlap and both brake hard at low speed
Person in traffica person in the path of moving traffic for 2 s

The live tracker follows vehicles only. The person rules therefore need a person tracker before they can fire on live video; intrusion zones catch vehicles today.

Counting vehicles

A tracker gives one vehicle several IDs: after an occlusion, when it boxes the same vehicle twice, or when it drops and re-acquires a parked car. anpr/track/vehicle_count.py (link_fragments) joins those back into one vehicle. It uses the plate reader's own merges, duplicate boxes in the same frames, continuations that start where a track was heading, and parked vehicles picked up again on the same spot. Boxes that never moved and never looked like a vehicle, such as a lane marking or the clock overlay, are not counted. On the CAM06 noon clip, 141 tracker IDs are 84 vehicles, checked by eye. It runs in the evidence tools, not in the live worker. Dense street scenes such as the Delhi clip are not yet linked reliably, so the Delhi video shows plates without a count.

Dashboard

The dashboard is the operator console: Next.js 14 (App Router), React 18, TypeScript and Tailwind, with react-leaflet for maps and hls.js for video. It is built as a standalone Node server on port 3000. Every page is a client component that calls the central API; there is no business logic in the dashboard.

Sign-in and requests

  1. middleware.ts sends any visitor without a vigentra_session cookie to /login. This is a convenience only; the central API does the real authorisation.
  2. The login page posts to the dashboard's own api/auth/login route, which signs in to the central API and stores the token in an httpOnly cookie that expires with it.
  3. The browser always calls /api/vigentra/… on the dashboard itself. That proxy route reads the cookie, adds the token and forwards the request to the central API, so page scripts never see the token.
  4. lib/api.ts holds every endpoint in one api object. A 401 sends the user back to sign in, unless it was a wrongly re-entered password.
  5. Sign-out clears the cookie.

The live wall

app/live/page.tsx and components/LiveTile.tsx. Starting the wall needs a reason. By default each tile is a still image refreshed every 2.5 seconds (0.6 seconds when a tile fills the screen), because the grid's video is too slow to stream thirty tiles at once. In video mode each tile waits for one of 12 start slots, opens its own session with the reason and password, retries with backoff, and closes the session when it scrolls out of view. Clicking a tile makes it full screen without opening a second session.

Known gaps

Fixed while writing this guide
  • The engine held every plate until the end of a pass, up to 1,500 frames for a continuous reader. Each plate now leaves on the frame its track closes.
  • Plate search and the route trace ignored the 30-day plate retention window. Both now stop at it.
  • Intrusion zones defaulted to people, whom the live tracker never follows. Zones now catch whatever the tracker follows.
  • The alerts page said it refreshed every 30 seconds; it refreshes every 5.
  • The design document named an outage demonstration that no longer applies, and claimed person intrusion on live video.
Still open
  • Live wall snapshots are not audited. In the default snapshot mode the reason is not sent and no audit row is written; only video mode audits each tile.
  • Person rules need a person tracker. Person in traffic and person intrusion cannot fire on live video until the tracker follows people.
  • The live reader needs a GPU. In Docker on this laptop a continuous CAM06 pass took 13 to 32 hours, too slow to settle plates.
  • Engine cache of 4. With about 30 cameras in all-camera mode, every camera reloads its engine each cycle.
  • A stalled capture skips the end of the pass, so that pass's unsent boxes are lost.
  • The edge worker has a built-in default password used when EDGE_PASSWORD is not set. It should be required instead.
  • Audit page paging filters after the limit, so a departmental reader can get short pages.
  • The health monitor polls sources one after another, so a slow source delays the others' checks.
  • Leftover code and comments. The providers/ package is built at start-up but unused. Some comments still describe an earlier "no video" phase, and the system_admin role's documented video rights differ from its permissions. Some comments in thresholds.yaml contradict the settings.
  • No database migrations yet, and no dashboard tests.

Where to start reading

For someone new to the code, this order follows one camera from the department to the screen:

  1. docker-compose.yml: what runs and how it connects.
  2. services/central-api/app/adapters/base.py, then traffic_adapter.py: how a department is federated.
  3. services/central-api/app/services/sync_service.py: how cameras arrive in the registry.
  4. services/central-api/app/services/video_permissions.py and video_broker.py: who may watch, and how.
  5. services/edge-worker/app/worker.py, function run: one camera pass at the edge.
  6. services/edge-worker/anpr/pipeline.py: the plate reader, from process_frame to _decide.
  7. services/central-api/app/routers/detections.py and services/watchlist_service.py: from a plate to an alert.
  8. services/dashboard/lib/api.ts, then app/alerts/page.tsx: how the console asks for it.

Glossary

ANPR
Automatic number plate recognition: finding and reading vehicle registration plates in video.
VMS
Video management system: a department's own software for its cameras, recordings and users.
Adapter
The code that translates one source system's dialect into Vigentra's canonical camera record.
RTSP
Real Time Streaming Protocol, how the edge pulls live video; forced onto TCP here.
PTS
Presentation timestamp: the time each frame carries in the stream, the only clock the edge trusts.
YOLO11
The object detector used for vehicles and plates.
ByteTrack
The tracker that gives each vehicle an ID across frames.
CRNN
A character-reading neural network; two of them read each plate crop.
ROVER
A voting method that aligns several readings and votes character by character.
Crop bank
The set of plate crops kept for one tracked vehicle, ranked by quality.
Sighting
One settled plate reading at one camera at one moment.
Watchlist
Plates to be told about: stolen, wanted, blacklisted, missing or suspect.
JWT
The signed token that proves who is signed in.
HMAC
The signature on each webhook alert, so a receiver can reject anything Vigentra did not send.
Discontinuity
The cut where a looping grid recording starts again; all tracking state is reset there.
